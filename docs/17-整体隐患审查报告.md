# 整体隐患审查报告

审查时间：2026-05-19
审查范围：Spring Boot 3 后端、Vue3 前端、MySQL、Docker Compose、上线前文档和自动验收脚本。
当前分支：`codex/mall-platform`

## 1. 总体结论

项目已经具备小规模实用商城的核心能力：用户下单、线下付款备注、管理员确认收款、发货、用户确认收货、取消待支付订单恢复库存、商品图片上传、后台基础运营、Docker Compose 运行和业务验收脚本。

但当前仍不建议直接作为正式生产环境上线。主要原因不是功能缺失，而是存在以下隐患：

- Docker Desktop + WSL 场景下，MySQL 初始化 SQL 单文件 bind mount 曾在 Docker 重启后失效，导致 MySQL 容器退出。
- `/api/health` 只证明后端进程存活，不能证明数据库可用，曾出现健康检查 200 但业务接口 500。
- 订单创建和订单取消缺少强幂等和状态条件更新，并发下可能出现重复订单或重复恢复库存。
- 生产配置仍容易误用演示默认值。
- 通用 500 错误会向前端暴露内部异常消息。
- 后端自动化测试覆盖不足，当前主要依赖端到端脚本。

## 3. 高风险隐患

### H1. MySQL 初始化 SQL 单文件 bind mount 在 Docker Desktop + WSL 场景下不稳定

涉及文件：

```text
docker-compose.yml
```

当前配置：

```yaml
volumes:
  - mall-mysql-data:/var/lib/mysql
  - ./mall-backend/src/main/resources/sql/schema.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro
  - ./mall-backend/src/main/resources/sql/data.sql:/docker-entrypoint-initdb.d/02-data.sql:ro
```

实测现象：

- Docker Desktop 重启后，`mall-mysql` 曾处于 `Exited (127)`。
- `docker inspect mall-mysql` 显示挂载初始化 SQL 文件时报错：

```text
not a directory: Are you trying to mount a directory onto a file (or vice-versa)?
```

影响：

- MySQL 退出，业务接口不可用。
- 后端容器仍可能保持运行，导致用户误以为系统正常。
- 在 Windows / WSL 共享目录部署或重启 Docker Desktop 后容易复现。

建议修复：

1. 新增 MySQL 初始化镜像，例如：

```text
mall-mysql/
  Dockerfile
```

2. 在 Dockerfile 中复制 SQL：

```dockerfile
FROM mysql:8.0
COPY ../mall-backend/src/main/resources/sql/schema.sql /docker-entrypoint-initdb.d/01-schema.sql
COPY ../mall-backend/src/main/resources/sql/data.sql /docker-entrypoint-initdb.d/02-data.sql
```

3. Compose 中改为：

```yaml
mysql:
  build:
    context: .
    dockerfile: mall-mysql/Dockerfile
```

4. 避免运行时挂载单个 SQL 文件。

优先级：最高。

### H2. 健康检查未覆盖数据库，存在假健康

涉及文件：

```text
mall-backend/src/main/java/com/example/mall/controller/HealthController.java
```

实测现象：

- MySQL 退出时，`GET /api/health` 返回 200。
- 同时 `GET /api/products?page=1&size=1` 返回 500。

影响：

- 部署脚本、反向代理、监控系统可能认为服务正常。
- 实际用户访问商品、下单、后台管理会失败。

建议修复：

- 保留轻量存活检查：`/api/health`。
- 新增就绪检查：`/api/ready`，检查数据库连接。
- Docker Compose 后端 healthcheck 使用 `/api/ready`。
- 文档中区分 liveness 和 readiness。

优先级：最高。

### H3. 订单并发幂等不足，可能重复下单或重复恢复库存

涉及文件：

```text
mall-backend/src/main/java/com/example/mall/service/impl/OrderServiceImpl.java
mall-backend/src/main/java/com/example/mall/mapper/ProductMapper.java
```

当前行为：

- 创建订单时，先读取购物车项，再扣库存，再删除购物车项。
- 取消订单时，先读取订单状态，再恢复库存和销量，再更新订单状态。

潜在问题：

- 用户双击提交或并发请求时，同一购物车项可能生成多笔订单。
- 并发取消同一待支付订单时，可能重复恢复库存。
- 状态流转依赖应用层判断，不是数据库条件更新。

建议修复：

- 订单创建引入幂等键，例如 `requestId` 或 `checkoutToken`。
- 结算购物车项时加锁，或使用结算状态字段。
- 订单状态流转改为条件更新：

```sql
UPDATE order_info
SET status = 4, cancel_time = NOW()
WHERE id = ? AND user_id = ? AND status = 0;
```

- 只有影响行数为 1 时才恢复库存。
- 管理员确认收款、发货、用户确认收货均使用 `WHERE status = ?` 条件更新。

优先级：最高。

## 4. 中高风险隐患

### M1. 生产配置仍容易误用演示默认值

涉及文件：

```text
docker-compose.yml
.env.example
mall-backend/src/main/resources/application.yml
mall-backend/src/main/resources/application-prod.yml
```

当前情况：

- Compose 默认 `SPRING_PROFILES_ACTIVE=dev`。
- Compose 内置演示数据库密码、演示 JWT secret。
- 默认 `CORS_ALLOWED_ORIGINS=*`。
- MySQL 使用 root 账号供应用连接。

影响：

- 如果用户直接把当前 Compose 部署到公网，可能误用演示安全配置。
- MySQL 端口默认映射到宿主机 `3307`，若安全组误开放会产生风险。

建议修复：

- 新增 `docker-compose.prod.yml`。
- 生产 Compose 使用 `${VAR:?required}` 强制必填。
- 生产环境禁止默认 JWT、默认 DB 密码和 `CORS=*`。
- 创建独立 MySQL 应用用户，不使用 root 作为应用连接账号。
- 生产环境默认不映射 MySQL 到宿主公网端口。

优先级：高。

### M2. 通用异常会向前端暴露内部错误

涉及文件：

```text
mall-backend/src/main/java/com/example/mall/exception/GlobalExceptionHandler.java
```

当前行为：

```java
return error(500, "系统错误：" + e.getMessage());
```

影响：

- 可能暴露 SQL 异常、文件路径、约束名、框架内部信息。
- 对真实上线不合适。

建议修复：

- 前端统一返回：

```text
系统暂时不可用，请稍后重试
```

- 后端日志记录完整异常。
- 增加 requestId，便于排查。

优先级：高。

### M3. Docker Hub 网络依赖会影响首次部署和 CI 构建

实测现象：

```text
failed to fetch oauth token: Post "https://auth.docker.io/token": connectex timeout
```

影响：

- 服务器首次 `docker compose build` 可能失败。
- 新机器或清理镜像后无法快速恢复。

建议修复：

- 文档中补充 Docker Hub 网络要求和镜像源/代理说明。
- 更推荐后续建立镜像发布流程：
  - GitHub Actions 构建后端、前端镜像。
  - 推送到 GitHub Container Registry 或 Docker Hub。
  - 服务器只执行 `docker compose pull && docker compose up -d`。

优先级：高。

## 5. 中风险隐患

### M4. 分页参数缺少范围限制

涉及文件：

```text
mall-backend/src/main/java/com/example/mall/dto/ProductQueryDTO.java
mall-backend/src/main/java/com/example/mall/dto/OrderQueryDTO.java
```

当前情况：

- `page`、`size` 没有 `@Min`、`@Max`。
- 外部请求可以传入很大的 `size`。

影响：

- 大分页可能拖慢数据库和后端。
- 恶意请求可造成资源消耗。

建议修复：

```java
@Min(1)
private Long page = 1L;

@Min(1)
@Max(100)
private Long size = 10L;
```

优先级：中。

### M5. 后台保存 DTO 对状态枚举约束不足

涉及文件：

```text
mall-backend/src/main/java/com/example/mall/dto/CategorySaveDTO.java
mall-backend/src/main/java/com/example/mall/dto/ProductSaveDTO.java
```

当前情况：

- `status` 可由请求体传入。
- 后端 Service 部分路径校验了状态，但新增/更新 DTO 本身没有枚举校验。

影响：

- 非法值可能落到数据库约束层，最终变成 500 或不友好的错误。

建议修复：

- 增加自定义校验注解或在 Service 中统一校验 `0/1`。
- 错误应返回 400。

优先级：中。

### M6. 自动化测试覆盖不足

当前情况：

- 后端没有 `src/test` 测试文件。
- 前端没有 spec/test 文件。
- 主要依赖 `scripts/practical-flow-check.mjs` 端到端脚本。

影响：

- 并发、异常、权限边界、状态流转回归难以及时发现。
- 验收脚本依赖固定种子用户和商品 ID。

建议修复：

- 增加后端集成测试：
  - 权限：未登录、普通用户访问后台、禁用用户 Token。
  - 订单：创建、取消、确认收款、发货、确认收货、非法状态流转。
  - 上传：格式、大小、伪造扩展名。
  - 参数校验：分页、状态枚举。
- 验收脚本改为先准备独立测试商品和测试用户，降低对固定 seed 的依赖。

优先级：中。

## 6. 低风险或可接受问题

### L1. 前端主包偏大

实测：

```text
dist/assets/index-*.js 约 1.2 MB，gzip 约 398 KB
```

影响：

- 小规模项目可接受。
- 首屏加载可能稍慢。

建议：

- 后续按路由拆分 Element Plus 或配置 manualChunks。

优先级：低。

### L2. 线下付款模式需要运营约束

当前项目未接真实支付，采用线下付款备注和管理员确认收款。

影响：

- 订单收款依赖人工核对。
- 不能自动处理退款、支付回调、支付超时关闭。

建议：

- 上线前明确收款账户、付款备注格式和管理员核对流程。
- 后续如接真实支付，需要重新设计支付单、回调验签、幂等处理和退款流程。

优先级：低到中，取决于真实业务需求。

## 7. 建议修复顺序

### 第一批：运行稳定性和上线防呆

1. 修复 MySQL 初始化 SQL 单文件 bind mount，改为自定义 MySQL 初始化镜像。
2. 增加数据库 readiness 检查。
3. 增加 `docker-compose.prod.yml`，生产必填配置强校验。
4. 收敛 500 错误信息。

### 第二批：交易一致性

1. 订单创建增加幂等键。
2. 订单状态流转改为条件更新。
3. 取消订单库存恢复和状态更新绑定到同一条件流转。
4. 补并发测试。

### 第三批：输入校验和测试

1. 补分页范围限制。
2. 补状态枚举校验。
3. 补后端集成测试。
4. 优化 `scripts/practical-flow-check.mjs` 的测试数据准备方式。

### 第四批：部署体验

1. 补 Docker Hub 网络/镜像源说明。
2. 后续建立镜像发布流程。
3. 服务器部署后增加备份定时任务示例。

## 8. 当前可接受上线边界

如果只是本地演示、课程展示或小规模内测，当前项目可继续使用。

如果要公开部署到云服务器，至少应先完成：

- H1：MySQL 初始化挂载稳定性修复。
- H2：数据库 readiness 检查。
- M1：生产 Compose 强防呆。
- M2：500 错误信息收敛。

如果要处理真实订单，应继续完成：

- H3：订单并发幂等修复。
- M6：订单和权限集成测试。
