# 阶段十二：登录会话安全加固

## 本阶段目标

基于 `docs/codex_next_development_prompt.md` 的 P2 要求，将登录鉴权从“基础 JWT 校验”升级为“具备基础上线安全能力”的会话机制。

本阶段优先完成：

- JWT 会话版本校验。
- 修改密码、主动退出登录和禁用用户后旧 Token 失效。
- 登录失败内存限流。
- 注册和修改密码的复杂度校验。
- 前端退出登录时调用后端失效接口。

## 修改内容

### 1. 用户表会话字段

`user` 表新增：

```sql
session_version INT NOT NULL DEFAULT 0
last_login_time DATETIME NULL
last_password_update_time DATETIME NULL
```

同步更新：

- `schema.sql`
- `migration/V20260520__session_security.sql`
- `User` 实体
- 数据库设计文档

### 2. JWT 会话版本

JWT 生成时写入 `sessionVersion` claim。拦截器解析 Token 后，会查询数据库中的用户记录，并比较：

```text
token.sessionVersion == user.sessionVersion
```

不一致时返回 401，提示重新登录。

### 3. Token 失效场景

以下操作会递增 `session_version`：

- 用户修改密码。
- 用户主动退出登录。
- 管理员禁用用户。

因此操作前签发的旧 Token 会被拒绝。

禁用用户仍保留原有状态检查：禁用期间旧 Token 返回 403；重新启用后，旧 Token 也会因为版本不一致返回 401。

### 4. 登录失败限流

新增内存限流组件 `LoginAttemptLimiter`：

- 同一用户名在 15 分钟窗口内连续失败 5 次后锁定。
- 锁定期间继续登录返回 HTTP 429。
- 正确登录会清理失败记录。

该方案适合单实例小规模内测。后续多实例部署时应替换为 Redis 或网关级限流。

### 5. 密码复杂度

注册和修改密码要求：

- 长度 8-30 位。
- 至少包含字母和数字。
- 不能与用户名相同。
- 修改密码时不能与旧密码相同。

### 6. 前端退出登录

前端 `auth.logout()` 改为先调用：

```text
POST /api/user/logout
```

无论远端接口是否成功，都会清理本地 `localStorage`，保证用户界面可靠退出。

## 兼容性影响

- 新环境直接执行 `schema.sql` 即可拥有新字段。
- 已有数据库需要执行 `V20260520__session_security.sql`。
- 旧版本签发的 JWT 不包含 `sessionVersion`，会按 `0` 处理；如果数据库中用户 `session_version` 仍为 `0`，旧 Token 可继续使用。用户改密、退出或被禁用后会失效。
- 注册弱密码会从过去的 6 位最小长度收紧为 8 位且必须包含字母和数字。
- 前端退出登录会多一次后端请求。

## 验证方式

建议执行：

```bash
git diff --check
cd mall-frontend && npm run build
cd ../mall-backend && mvn -B test
```

运行态验收：

```bash
docker compose up -d --build
node scripts/practical-flow-check.mjs
```

脚本已新增覆盖：

- `/api/ready` 数据库就绪检查。
- 连续错误登录后返回 429。
- 修改密码后旧 Token 返回 401。
- 主动退出登录后旧 Token 返回 401。

## 未完成与风险

- 登录失败限流是内存实现，重启后清空，多实例部署时各实例不共享。
- 尚未实现 refresh token、HttpOnly Cookie、CSRF Token 或 Token 黑名单表。
- 管理员敏感操作二次确认目前主要由前端交互承担，后端尚未要求二次密码确认。
- 还未实现下单 `requestId` 幂等和库存流水。
