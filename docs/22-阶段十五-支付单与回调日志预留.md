# 阶段十五：支付单与回调日志预留

## 目标

本阶段补齐订单支付相关的数据模型，为线下收款留存可审计支付单，并为后续接入微信、支付宝等第三方支付回调预留落库结构。

当前实现仍以演示和管理后台线下确认收款为主，不代表已经完成第三方支付接入。

## 修改内容

- 新增 `payment_order` 支付单表，用于记录订单对应的支付流水。
- 新增 `payment_callback_log` 支付回调日志表，用于保存第三方支付回调原文和处理结果。
- 管理员确认线下收款后，系统会自动生成一条 `OFFLINE` 渠道的成功支付单。
- 补充数据库迁移脚本、实体、Mapper、接口测试观察点和数据库设计文档。

## 支付单表

`payment_order` 用于承载订单支付状态和支付渠道信息。

关键字段：

- `order_id`：关联 `order_info.id`。
- `order_no`：冗余订单号，便于排查和对账。
- `payment_no`：支付单号，全局唯一。
- `channel`：支付渠道，当前线下确认收款使用 `OFFLINE`。
- `amount`：支付金额，当前取订单总金额。
- `status`：支付状态，当前成功支付使用 `1`。
- `paid_time`：支付成功时间。
- `third_party_trade_no`：第三方交易号或线下付款备注。

## 回调日志表

`payment_callback_log` 用于后续接入真实支付网关时保存回调记录。

关键字段：

- `payment_no`：关联业务侧支付单号。
- `channel`：支付渠道。
- `event_type`：回调事件类型。
- `raw_payload`：回调原文。
- `verify_result`：签名或来源校验结果。
- `process_result`：业务处理结果。

该表目前只完成结构预留，暂未接入实际回调接口。

## 线下收款流程

管理员调用确认收款接口后：

1. 订单状态更新为待发货。
2. 订单 `pay_time` 写入当前时间。
3. 系统插入一条 `payment_order`。
4. 支付单字段约定：
   - `channel = OFFLINE`
   - `status = 1`
   - `amount = order_info.total_amount`
   - `third_party_trade_no = order_info.payment_note`

## 兼容性影响

- 已有订单表结构未修改。
- 线下确认收款接口的响应结构未修改。
- 新增表依赖 `order_info(id)`，迁移时需要先确保订单表已经存在。
- 如果重复调用确认收款接口，既有订单状态校验会阻止重复生成线下支付单。

## 验证方式

建议验证点：

1. 执行数据库迁移脚本成功。
2. 创建订单并上传付款凭证。
3. 管理员确认收款。
4. 观察订单进入待发货状态。
5. 查询 `payment_order`，确认生成一条 `OFFLINE` 成功支付单。
6. 确认 `payment_callback_log` 表存在，后续可用于真实支付回调落库。
