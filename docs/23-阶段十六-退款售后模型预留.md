# 阶段十六：退款售后模型预留

## 目标

本阶段补齐退款和售后的基础数据模型，为后续实现已支付未发货取消、已发货退款申请、管理员审核、退款中、退款成功或失败等流程做结构准备。

当前阶段只完成表结构、实体、Mapper 和文档预留，不代表退款接口、退款回调或库存恢复业务已经完成。

## 修改内容

- 新增 `refund_order` 退款售后单表。
- 新增 `refund_operation_log` 退款售后操作日志表。
- 新增对应 MyBatis-Plus 实体和 Mapper。
- 新增增量迁移脚本。
- 更新 README、数据库设计、迁移说明和测试报告。

## 退款售后单表

`refund_order` 用于记录退款申请和退款处理状态。

关键字段：

- `refund_no`：退款售后单号，全局唯一。
- `order_id`、`order_no`：关联并冗余订单信息，便于排查。
- `user_id`：申请退款的用户。
- `payment_no`：可选关联原支付单。
- `apply_type`：退款类型，`0` 表示仅退款，`1` 表示退货退款。
- `refund_amount`：退款金额，必须大于 0。
- `status`：退款售后状态。
- `stock_restore_required`：是否需要恢复库存。
- `stock_restored`：库存是否已经恢复。
- `audit_time`、`refund_time`、`finish_time`：关键流转时间。

状态约定：

```text
0 申请中
1 审核通过
2 审核拒绝
3 退款中
4 退款成功
5 退款失败
6 已取消
```

## 操作日志表

`refund_operation_log` 用于保存退款售后状态流转历史。

关键字段：

- `refund_id`、`refund_no`：关联退款售后单。
- `operator_id`：操作用户，可为空以表示系统操作。
- `operator_role`：操作角色，只允许 `USER`、`ADMIN`、`SYSTEM`。
- `from_status`、`to_status`：状态流转前后值。
- `action`：操作动作，例如申请、审核通过、审核拒绝、退款成功。
- `remark`：操作备注。

## 兼容性影响

- 不修改现有订单、支付、库存接口。
- 不改变前端请求字段和响应结构。
- 新表依赖 `order_info`、`user` 和 `payment_order`，已有数据库需要先执行支付模型迁移。
- 当前不自动恢复库存；后续实现退款成功并需要恢复库存时，应同时写入 `stock_movement`。

## 验证方式

建议验证点：

1. 执行迁移脚本成功。
2. 检查 `refund_order` 存在唯一索引 `uk_refund_no`。
3. 检查 `refund_order` 能关联 `order_info`、`user` 和可选 `payment_order`。
4. 检查 `refund_operation_log` 能关联退款售后单。
5. 检查 `refund_amount`、`status`、`operator_role` 等约束能阻止非法值。
